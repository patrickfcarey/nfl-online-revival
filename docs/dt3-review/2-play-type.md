# DT-3 lane 2 — what `0x0015ada0` actually returns
**VERDICT: UNDETERMINED-NEEDS-LIVE-READ for the *name* of type 2 — but its *scope* is settled enough to act on: on both DT regression savestates the getter returns **0**, not 2, so nopping `0x001f4ae8` changes nothing on either, and the patch is very likely a no-op on ordinary run and pass plays.**

**1. The chain (verified, `extract/SLUS_207.52`).** `0x0015ada0` → `0x00154790` (screen id): id `0x0E` ⇒ 3 ⇒ returns `[[0x00600C70]+0x98]` via `0x001485d8` — dead during play, the in-play screen id reads **2**. Else → `0x0015ade0` → `0x0015b418`, which walks offensive slots 0..10 (`0x001655b0`) and returns the first player whose class ≠ 0, then classifies him with `0x0015aeb8`. That reads the **authored play record** at `[0x00609770] + side*0xAFBC + 0x1400 + idx*40 + 0x3F` (`0x00248360` then `0x00243c98`), masks bit 7 (`s1 = -129`), and maps: `byte+0` 55 → **3**, 54 → **2**, 45 → **1** (or **5** when `[[0x00601f4c]+141] == -2`); `byte+4` 45 → **4**, which overrides everything; otherwise **0**. Nothing per-frame is read — it is a property of the called play, exactly as `addresses.yaml` says.

**2. What the stored byte is.** Record bytes +0/+4 are **AI-state ids** in the same namespace as `docs/state-dispatch-table.md`: states 45/54/55 are one family sharing `can_leave 0x001b3248` / `ai_think 0x001b3290` / `user_think 0x00268640`, and their *enter* stubs store this very enum at `player+0x150` through `0x001b2e10(player, kind, record[1])` — 55→3, 54→2, 45→5 if `[0x00260a38()+25] == -2` else 4/1. So `0x0015ada0` = "which member of that state family the play authors on offence", 0 = none. The family is **not identified** (unverified): no strings, no name table, and no hardcoded 45/54/55 setter exists. **Writers of the storage: NOT FOUND (unverified)** — cross-function store tracking over all 108 `0x00248360` callers and all 13 `0x00243c98` callers finds none, and the two `+5183` sites (`0x002e0218`, `0x002e0bb0`) are unrelated halfword stores; the array is filled by the play loader, so the possible values are **play-file content and cannot be enumerated from the ELF**. The vocabulary below is therefore the readers' vocabulary, not the writers'.

Grouping across the 8 jump tables and two range tests: **{1,4,5}** behave as one class (5 of 8 tables; the other two split {1,5} / {3,4}), **2 and 3 are siblings** (`0x0015ae4c`'s table; `0x001f57e4` `sltiu(v0-2, 2)`; `0x001f5fc4`/`0x001f5fd8` early-returns on 3 **or** 2). That matches the state layer: 54 and 55 are twins, 45 is the odd one that fans out to 1/4/5. **No caller does "beq 2 → skip pass-only code", so type 2 cannot be placed in a run/pass family from the census** — that inference is not available.

**4. Blast radius of the nop.** Patch mechanics are right: `beq` (not `beql`), so the delay slot `daddu s2, zero, zero` still executes, and `0x001f4c04` is the epilogue of `0x001f4790`, so value 2 is an early return that skips phase 3 (the 11-player kind-{2,3,4,5,6} scan that assigns helpers via `0x001f7398(a2=7)`). `0x001f4adc` is the **only** `0x0015ada0` call inside `0x001f4790`–`0x001f4c38`; `0x001f4710` is in the *previous* function. **But two sibling gates in the same blocking module still treat 2 and 3 as one class** — `0x001f57e4` and `0x001f5fc4/…fd8` — so after the patch a type-2 play runs helper assignment while those two still bail: one gate open, two closed, i.e. **the nop does create an inconsistent state** (consequence unverified). Reach: measured on `extract/ee_inplay.bin` and on eeMemory extracted from `lead_blocker_slot6.p2s` (run: OL 33, WR 3→47, RG 72) and `pass_protection_slot7.p2s` (pass: OL 31, WR 19→20, QB →18) — **no offensive player authors 45/54/55 in either, so the getter returns 0 in both**. Type 2 is therefore **not** "most plays"; it is a narrow family, and DT-3 as deployed most likely does nothing on slot 9 either. Caveat, flagged: all four samples are pre-snap (`frames_since_snap = 0`), and it is **unverified** whether the record array is rewritten after the snap.

**5. The one live read that settles it** (run at snap+30 on slot 9, then slot 7, then slot 6; sample *post*-snap, not only pre-snap): `side = byte[[0x00601f4c]+0x90]`, `base = word[0x00609770]`, then for `i` in 0..10 read `c0 = byte[base + side*0xAFBC + 0x1400 + 40*i + 0x3F]` and `c4 = byte[…+4]`; the first `i` with `(c4 & 0x7F) == 45` gives 4, else `(c0 & 0x7F)`: 55→3, 54→2, 45→1 (5 if `sbyte[[0x00601f4c]+141] == -2`), none→0. In the current dumps that block sits at `0x006AABAF`, stride 40, 11 entries — **re-read the pointer, do not hardcode it**.
